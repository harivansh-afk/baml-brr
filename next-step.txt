The next experiment

Start by defining the comparison: faster execution of which programs, on which
native and browser targets, with what telemetry and isolation requirements?
Record current BEX behavior and timings before choosing a winning backend.
Keep compilation time separate from execution time.

First, trace one BAML function through the checked source and MIR. Use a loop
that calls another function and updates a local. For each operation, record
what the type checker already decided, what MIR lowering adds, and what the
Rust generator would need to emit. Then repeat with deferred cleanup or a
captured variable. That is where the difference becomes interesting.

Rust's compiler can optimize the Rust we give it: inline functions, simplify
branches, allocate CPU registers, and emit machine code. It does not know
BAML's rules for integer overflow, shared objects, cleanup, or task suspension.
Those must be expressed correctly by our generator and runtime first.

For the MIR route, translate the function's blocks into a Rust loop/match
dispatcher. Once that works, try expressing the ordinary loop as a Rust loop.
This checks whether remaining block dispatch matters for this program.

For the typed route, preserve the loop directly and consume the checker's
resolved types and calls. Record every piece of behavior we have to reproduce
from MIR lowering. Where it makes sense, share that operation with the existing
compiler instead of maintaining two separate definitions of BAML behavior.
We are not removing MIR from the interpreter's compilation path.

Keep both emitters in one experimental compiler crate with separate modules.
Use the same arithmetic helpers, value representation, and build flags.
Start with integers, booleans, locals, branches, loops, and direct calls.
Reject unsupported features rather than silently executing them differently.
No broad crate rearrangement is needed for this first step.

Rust is the leading candidate from the team notes, not the only candidate.
Use the same small program for bounded C/Clang and direct LLVM probes, comparing
how much translation they require. Check a Wasm output path early if browser
delivery is required. Direct Wasm emission is a separate candidate from having
Rust or Clang emit Wasm for us. Cranelift becomes especially useful to compare
when compilation latency or dynamically supplied code matters.

Run each program through BEX and both generated versions. Check results,
including edge cases. Measure BAML-to-Rust generation, rustc compilation,
and execution separately. Keep inputs unknown until runtime and consume the
outputs. Compare equivalent timed regions; the engine call and a bare Rust
function include different work.

Next add an array shared by two variables, an object surviving collection,
and one pause/resume case. Extract only the runtime operations these require.
The heap is already separate; builtins and engine execution still depend on
BexVm. This integration is shared work for both emitters.

After that, compare speed, build time, size, and duplicated compiler logic.
Choose a route to extend. Keep the interpreter as the behavior reference.
An early arithmetic win alone does not settle the backend choice.

These probes are a proposed way to test the notes' assumptions. They are not
a claim that the team approved equally sized implementations of every backend.
